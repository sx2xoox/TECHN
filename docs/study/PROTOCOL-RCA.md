# 연구 계획서 2: 여러 시스템에 번진 장애의 근본 원인 찾기

판: 1.0 · 도구: `STUDY_TASK=rca npm run study`(이 저장소의 같은 커밋) · 첫 실험([PROTOCOL.md](PROTOCOL.md))과 **따로** 등록하고 따로 분석합니다. 바꾸면 날짜와 이유를 '변경 기록'에 남깁니다.

## 1. 왜 두 번째 실험인가

첫 실험은 "규칙을 어긴 곳 하나를 찾기"를 잽니다. 그런데 ISOMORPH 의 최신 주장은 그보다 큽니다. 클러스터(Kubernetes)와 서비스(OpenTelemetry)를 한 세계로 묶고, 실패한 곳에서 **장애가 처음 시작된 곳까지** 거슬러 올라가 보여준다는 것입니다. 이 실험은 그 주장을 사람으로 잽니다.

## 2. 질문과 가설

**질문**: 고객 화면(frontend 서비스)이 실패할 때, 사람들은 근본 원인(노드·디플로이먼트·서비스 중 하나)을 세계에서 관리 화면(표)보다 빨리, 덜 틀리게 찾는가?

- **H1(주 가설, 시간)**: 근본 원인을 맞게 고른 과제의 시간은 세계가 표보다 짧다. 판정 기준은 첫 실험과 같습니다(참가자별 '세계/표' 중앙 시간 비율 중앙값의 부트스트랩 95% 구간 상한 ≤ 0.5 → 50% 단축).
- **H2(부 가설, 정확도)**: 근본 원인을 맞게 고른 비율은 세계가 표보다 낮지 않다.
- **H3(분해, 양측·방향 없음)**: 세계 대 '표 + 위반 강조 + 같은 살펴보기'. 엔진이 계산한 진단·근본 원인 사슬을 **두 조건이 똑같이** 받으므로, 이 비교는 "마을 그림 자체가 더하는 것"만 봅니다.
  - 차이가 없으면 이득은 그림이 아니라 엔진의 인과 계산에서 나온 것으로 보고합니다. 이 결론도 가치 있는 결과입니다.

## 3. 조건(세 가지 모두 권장)

| 조건 | 원본 표·값 | 변경 기록(최근 10분) | 위반 강조 | 엔진의 살펴보기(진단·근본 원인 사슬·직전 변경) | 마을 그림 |
|---|---|---|---|---|---|
| `world` | 말풍선으로 | 예 | 그림 속 이상 현상 | 예 | 예 |
| `table` | 예 | 예 | 아니요 | **아니요** | 아니요 |
| `table+alerts` | 예 | 예 | 붉은 행 + ⚠ | 예(세계와 같은 글) | 아니요 |

- **같은 원자료**: 세 조건 모두 같은 행과 같은 변경 기록을 받습니다. 서버가 조건별로 보내는 것을 시험이 확인합니다(`packages/server/test/study-rca.test.ts`).
- **같은 글**: 살펴보기 글에는 세계의 비유 이름(공장 등)을 쓰지 않고 원본 컬렉션 이름만 씁니다(시험이 확인).
- **같은 넓이**: 세계 캔버스는 표가 쓰는 본 영역을 그대로 채웁니다.
- **켜는 법**: `STUDY_TASK=rca STUDY_CONDITIONS=world,table,table+alerts STUDY_DATA=data/study-rca npm run study`. 기록 폴더는 첫 실험과 나눕니다(분석도 과제 종류별로 따로 합니다).

## 4. 과제

- **장면**: 실제 Kubernetes·OpenTelemetry 어댑터의 스키마와 여러 시스템 묶기(자동 연결 포함)를 그대로 쓴 정적 장면입니다.
  - 구성: 노드 3, 디플로이먼트 6(고객 화면 + 백엔드 4 + 배치 작업 1), 파드 약 15, 서비스 5.
  - 10분 동안의 관측 10개로 만들며, 이어진 두 관측의 차이가 변경 기록이 됩니다.
- **근본 원인 3종**(조건마다 한 번씩, 순서는 라틴 방진으로 돌림):
  1. **잘못된 배포**(정답: 그 디플로이먼트): 이미지를 바꾼 직후 새 파드가 뜨지 못해 준비된 복제본이 0이 되고, 그 서비스가 실패하고, frontend 가 실패합니다.
  2. **노드 고장**(정답: 그 노드): 노드가 멈추고, 그 위의 파드가 준비를 잃고, 복제본이 모두 그 노드에 있던 앱이 멈추고, frontend 가 실패합니다. 일부 복제본만 잃은 다른 앱들도 모자라집니다.
  3. **서비스 코드 오류**(정답: 그 서비스): 배포·노드는 그대로인데 서비스가 실패하고 frontend 가 실패합니다.
- **헷갈리게 하는 것(모든 장면에 있음)**:
  - 장애보다 5분 먼저 깨진, 상관없는 배치 작업 파드(가장 이른 위반이지만 근본 원인이 아님).
  - 장애 1분 전의 상관없는 정상 배포(이미지 변경).
  - 서비스 지연 시간 잡음.
- **답하는 법**: 근본 원인 하나를 고르고 원인 종류(배포·노드·서비스 코드)를 고른 뒤 제출합니다. '모르겠어요'로 넘어갈 수 있습니다. 제한 시간은 3분입니다.
- **연습**: 조건마다 1과제를 먼저 풀고, 이때만 정답을 알려줍니다.
- **분량**: 3조건 × (연습 1 + 본 과제 3) = 12과제이며 약 25분입니다. 2조건으로 하면 약 18분입니다.

## 5. 참가자

- **대상**: 만 19세 이상. 이 실험은 운영 지식(노드·배포)을 조금 요구하므로, 개발 경험이 있는 사람과 없는 사람을 모두 받습니다. 읽는 법 카드를 늘 보여줍니다.
- **주 분석 대상**: 완료 참가자 전체입니다. 개발 경험 집단(없음·조금·업무)별 결과는 부 분석으로 봅니다.
- **표본 크기**: 예비 실험 뒤 `npm run study:power` 로 정해 사전 등록 때 고정합니다. 첫 실험과 같은 기준(KPI 판정 확률 80%)을 씁니다.

## 6. 분석

- `npm run study:analyze -- data/study-rca --task rca --out report-rca.md --csv trials-rca.csv`
- **주 분석**: 참가자별 '정답 과제 중앙 시간'을 짝지은 윌콕슨 부호 순위 검정(양측, α=0.05)과 효과 크기 r, 그리고 비율 중앙값의 부트스트랩 95% 구간입니다.
- **정확도**: '위치 정확도'는 근본 원인 행을 맞게 골랐는가, '원인 정확도'는 종류를 맞게 골랐는가입니다.
  - 종류는 근본 원인이 노드·디플로이먼트·서비스 중 무엇인지와 거의 겹치므로, 주 지표는 위치 정확도입니다.
- **증상을 원인으로 고른 비율**: frontend 나 중간 서비스를 고른 경우입니다. 과제별 기록의 `answer` 로 따로 셉니다(탐색).
- 제외 기준·멈추는 규칙·공개 원칙은 첫 실험과 같습니다.

## 7. 엔진에 대해 미리 밝혀 둘 것(중요한 한계)

- **기본 장면에서 엔진은 늘 맞습니다.** 만들어지는 모든 장면에서, 실패한 frontend 를 누르면 나오는 근본 원인 사슬의 끝이 심은 근본 원인입니다. 시험이 원인 3종 × 시드 20개를 모두 확인합니다.
  - 노드 고장은 디플로이먼트와 노드가 파드로만 이어집니다. 그래서 이번에 추가한 '함께 기댄 곳' 규칙(디플로이먼트 ← 파드 → 노드)이 있어야 노드까지 갑니다.
  - 따라서 세계·표+위반 강조 조건의 결과는 **엔진이 맞을 때의 최선**입니다.
- **실제 시스템에서는 엔진이 틀리거나 중간에서 멈출 수 있습니다.** 트레이스가 없거나, 원인이 관측하지 않는 곳에 있는 경우입니다.
  - 근본 원인 벤치마크(`npm run bench:rca`)에서 엔진은 합성 장애의 77%를 맞히고, 6%는 덜 가고, 17%(트레이스 없음)는 아무것도 짚지 않습니다. 경로 밖을 짚는 경우는 0% 입니다.
  - 그래서 7-1절의 '엔진이 끝까지 못 가는 과제'로 과신을 따로 잽니다.
- 화면 안내에는 "엔진이 틀리거나 끝까지 찾지 못할 수도 있으니 판단은 여러분이 하세요"라고 씁니다.

## 7-1. 엔진을 과신하는가(선택, `STUDY_RCA_HARD=1`)

- **과제**: 조건마다 본 과제 하나를 더 넣습니다. 노드 고장이지만 클러스터가 늦게 알아챈 장면입니다(노드 감시 지연).
  - 엔진의 사슬은 frontend ← 서비스에서 멈추고, 참된 근본 원인은 노드입니다.
  - 변경 기록에는 노드가 준비를 잃은 줄이 있어 사람은 더 찾을 수 있습니다.
- **자리**: 블록 안 자리는 참가자·조건마다 돌립니다.
- **기록**: 과제마다 엔진의 결과(맞음·덜 감·멈춤·틀림)와 '엔진이 짚은 곳을 그대로 답했는가'(`followedEngine`)를 서버에서 남깁니다. 화면에는 보내지 않습니다.
- **분석**(사전에 정함):
  - 이 과제는 주 분석(H1·H2)에서 뺍니다.
  - 따로 조건별로 근본 원인 정확도와 '엔진이 짚은 곳을 답한' 비율을 보고합니다.
  - 표 조건은 엔진을 보지 않으므로, 같은 서비스를 답한 비율이 기준선(증상을 원인으로 고르는 비율)입니다.
  - 세계·표+위반 강조에서 이 비율이 기준선보다 높으면 과신으로 해석합니다. 참가자 안 비교(McNemar 등)는 탐색 분석입니다.
- **화면 문구**: 사슬 아래에 늘 "사슬은 근거가 있는 데까지만 오릅니다. 끝이 곧 근본 원인이라는 보장은 아닙니다." 라고 적습니다. 이 문구도 처치의 일부입니다.

## 8. 위험과 한계

첫 실험과 같습니다(최소 위험, 색 의존, 설계자 편향). 결과는 이 장면 구성과 원인 3종, 이 표 디자인에 한정됩니다.
